你的构想整体可行，但需要拆成两条路线来评估：**“字幕覆盖”路线是现实且值得投入的；“直接替换音频输出为中文语音”路线在实时场景下可行性很低**，不建议作为第一版目标。下面按模块拆解具体会用到的技术、可行方案和需要注意的地方。

---

## 整体架构判断

推荐的可行架构是一条“流水线”：

```
系统音频 monitor 捕获
        ↓
VAD 语音活动检测 + 分段
        ↓
流式/准实时 STT（Whisper 系）
        ↓
英→中机器翻译
        ↓
桌面字幕渲染（或送入 mpv/VLC）
```

关键认知是：**Whisper 本身不是“流式”模型**。所谓实时 Whisper，都是靠 VAD 把音频切成有意义的语音段，再对每个语音段做推理，从而模拟出“准实时”的效果。这意味着端到端延迟不可能做到像人类同传那样低，通常会有 1～3 秒的滞后，具体取决于模型大小和分段策略。

---

## 模块一：系统音频捕获（Debian 12）

Debian 12 桌面默认使用 PipeWire，同时提供 PulseAudio 兼容层。捕获“当前系统正在播放的声音”最直接的方式是抓取默认输出 sink 的 **monitor source**。

**可行方案（按推荐优先级）：**

1. **`parec` / `pw-record` 命令行管道**：这是最简单、依赖最少的方式。`parec` 是 PulseAudio 工具集的一部分，在 PipeWire 系统上通过 `pipewire-pulse` 兼容层同样可用，直接抓取默认 sink 的 monitor 源，把 PCM 流交给后续处理。你用 Python 的 `subprocess` 起一个 `parec` 进程，从 stdout 读 PCM 数据即可。
2. **`flexaudio`（Python 绑定，Rust 底层）** ：`flexaudio.open("system")` 可以直接打开全系统输出环回，并且支持 `chunk_ms=20` 的细粒度分块，底层通过 PipeWire 获取数据，API 设计对实时流比较友好。如果你的系统 PipeWire 版本兼容，这是一个比直接调 `parec` 更结构化的选择。
3. **`python-soundcard`**：Debian 仓库中有 `python3-soundcard`，底层依赖 `pipewire-pulse` 或 `pulseaudio`，可以用 `SoundCard(include_loopback=True)` 的方式拿到环回设备。但它的环回设备枚举在 PipeWire 下有时不够直观，不如前两种直接。

**需要注意：**

- 如果 PipeWire 的默认配置没有暴露 monitor source，你可能需要用 `pactl list sources short` 确认 `.monitor` 源是否存在。通常存在，但少数桌面环境或自定义配置下可能需要显式加载 `module-loopback` 或调整 `stream.capture.sink = true` 的 loopback 配置。
- **不要走“虚拟 sink + 把系统输出路由进去”的方案**来捕获——那会改变你实际听到声音的路由，增加故障点。直接抓 monitor source 是侵入性最小的做法。

## 模块二：流式语音识别（STT）

这是整条流水线中延迟和资源消耗的大头。

**引擎选择：`faster-whisper` 是当前 Debian 桌面上最务实的选择。** 它基于 CTranslate2，在相同准确率下比原版 Whisper 快 4～6 倍，CPU 和 NVIDIA GPU 都能用，INT8 量化后模型体积和内存占用也显著降低。

**模型大小的取舍（关键决策）：**

| 模型 | INT8 体积 | 适用场景 | 实时性参考 |
|---|---|---|---|
| `base` / `base.en` | ~145 MB | CPU 实时字幕的最低门槛 | 可接近实时，但准确率一般 |
| `small` / `small.en` | ~484 MB | **CPU 桌面实时字幕的推荐起点** | 多数现代 CPU 上可做到 1～3 秒延迟 |
| `medium` | ~1.5 GB | CPU 偏吃力，有 GPU 时可用 | 准确率明显提升 |
| `large-v3-turbo` | ~1.6 GB | **推荐 CUDA 场景**，性价比高 | GPU 上延迟可控 |

数据来源：faster-whisper 的模型体积和推荐场景。

**推荐组合：`small.en` + Silero VAD。** 你处理的是英文视频，`.en` 模型专门针对英文，在同等体积下准确率优于多语言模型；同时用 VAD 只在检测到人声时触发识别，避免把静音、音乐、音效送入 Whisper 产生幻觉（Whisper 在静音段“编造”出 “Thank you.” “Subscribe.” 是常见问题，现有的翻译字幕项目会专门做 hallucination filtering）。Silero VAD 与能量过滤结合的方案可以把误触发降低约 34%。

**如果不想自己拼装：WhisperLive。** 它是一个包装好的 WebSocket 服务，后端可选 `faster_whisper`、`tensorrt`、`openvino`，默认 `faster_whisper`，支持原始 PCM 输入。你可以把 `parec` 的 PCM 流通过本地 WebSocket 喂给它，省去自己管理 VAD 和分段逻辑。但它是一个服务端架构，对你的“单机桌面小工具”而言可能略显重型；如果打算做得干净、可维护，值得考虑。

## 模块三：英→中机器翻译

**本地翻译的可行选择是 NLLB-200 或 Opus-MT，二者都可以通过 CTranslate2 加速。**

- **Opus-MT**：英→中双语专用模型，体积小，延迟低，适合追求低延迟的实时场景。缺点是质量不是 SOTA，但在“看视频够用”这个标准下通常可以接受。
- **NLLB-200**：多语言覆盖广，有 600M 和 1.3B 版本。通过 CTranslate2 推理，英译中的延迟实测大约在 **300～800 ms** 量级，端到端（含识别）可以控制在 1.2～1.7 秒左右。600M 蒸馏版本在 CPU 上也可以跑。

**推荐策略：** 先用 **Opus-MT + CTranslate2** 跑通端到端延迟，如果质量不满意再换 NLLB-200 600M。翻译这一步的延迟通常不是瓶颈，STT 才是；不要在翻译模型上过早过度投入。

**需要注意：** 逐句翻译会丢失跨句上下文，代词、省略、时态在长对话中可能译得不自然。但对于“看视频理解内容”的目标，逐句翻译是可接受的起点。如果后续要优化，可以维护一个滑动窗口的上下文，把前一两句作为翻译模型的参考前缀。

## 模块四：桌面字幕渲染

你有两条路可选，取决于你是否想绑定特定播放器。

### 路线 A：通用桌面 OSD（推荐，不绑定播放器）

用 **PyQt6** 创建一个透明、无边框、总在最前的窗口，把翻译文本渲染在屏幕底部。已有的 `translation-overlay` 项目正是这个思路：捕获 PipeWire 系统音频 → 本地翻译模型 → PyQt 透明置顶字幕层，带打字机效果和旧行淡出。它目前调的是 Meta SeamlessM4T / faster-whisper，语言对可配置，架构可以直接借鉴。

另一种更轻量的方式是 **DBus OSD**（如 `gnome-osd` 或 `aosd-cat`），不需要自己管理窗口，但样式和排版控制力弱，不适合长时间连续字幕。

**PyQt6 方案的注意点：** 透明置顶窗口在不同 Wayland compositor 下的行为可能有差异（窗口置顶、点击穿透、多显示器定位），在 GNOME/KDE 上基本可用，但需要在你的实际桌面环境上验证。如果遇到问题，回退到 `mpv` 内嵌字幕是更稳妥的方案。

### 路线 B：绑定 `mpv` / VLC 的字幕轨

如果你主要用 `mpv` 看视频，可以把翻译结果写成临时 `.srt` 文件并让 mpv 加载，或者通过 mpv 的 IPC 接口动态更新字幕文本。mpv 有 Lua 脚本机制，已经有 `whispersubs.lua` 这类“本地 AI 字幕”脚本的先例，会在播放时调用 `whisper-cli` 生成字幕。`python-mpv` 也可以通过 ctypes 绑定控制 mpv 的属性、事件和字幕轨。

这条路线的好处是字幕渲染完全交给播放器，稳定、同步性好；代价是只能覆盖用 mpv/VLC 播放的内容，浏览器里的视频就不适用了。

**推荐顺序：** 先做 **PyQt6 通用 OSD**，这样浏览器、本地播放器、任何发声应用都能覆盖；如果 OSD 在你的桌面环境上不稳定，再退到 mpv 字幕轨方案。

## 模块五：直接替换音频为中文语音——为什么不可行 / 不建议

你提到的“直接替换当前音频输出为中文的翻译”，在实时视频场景下面临几个结构性障碍：

1. **延迟不可接受。** 即使是最乐观的语音克隆/TTS 方案，端到端也需要数秒。GPT-SoVITS 在 RTX 3060 上开启优化后可以做到 <500 ms，但这是在理想条件下的纯 TTS 延迟；叠加 STT 和翻译后，整条链路会达到数秒级。有实测指出，在 RTX 3090 上合成约 10 秒语音，总延迟普遍在 3.5～6 秒，远超实时交互的 200ms 阈值。
2. **音色保持与“替换”的语义矛盾。** 如果你想“听起来还是原来那个人的声音”，需要**语音转换（voice conversion）** 而非语音克隆；如果你接受用另一个声音朗读中文，那就是 TTS，和原视频的唇形、语气、情感完全脱节，观感会很不自然。
3. **与视频时间轴的对齐极其困难。** 视频的语速、停顿、音乐、音效都是原声的一部分。替换人声后，要么保留原背景音（需要人声分离），要么整体替换（丢失音效），工程复杂度急剧上升。
4. **资源消耗。** 语音克隆模型（如 GPT-SoVITS）需要 GPU，显存占用可观，与 STT + 翻译模型同时驻留时，桌面级 GPU 可能吃紧。

**结论：** “音频替换”可以作为远期探索方向，但不应该出现在第一版的设计里。第一版把“**准实时中文字幕**”做好，已经能解决你看英文视频的核心痛点。如果后续确实想要中文语音，更务实的做法是**离线/半离线后处理**：先把视频看完或下载下来，再用 STT→翻译→TTS 生成一条中文音轨，而不是在播放时实时替换。

## 分阶段路线建议

**第一阶段（1～2 天，验证可行性）** 用 `parec` 抓 monitor，管道送入 `faster-whisper small.en`，每 2～3 秒输出一段英文文本打印到终端。确认音频能抓到、识别准确率可接受、延迟心中有数。

**第二阶段（2～3 天，加上翻译和字幕）** 接入 Opus-MT + CTranslate2，把翻译结果用 PyQt6 透明 OSD 显示。这一步结束后，你已经有一个可用的“英→中桌面字幕器”。

**第三阶段（按需优化）** 根据实际体验调整：如果延迟高，降模型或调 VAD 分段策略；如果翻译质量差，换 NLLB-200；如果 OSD 在 Wayland 下有兼容问题，改走 mpv 字幕轨；如果 CPU 吃紧，考虑 GPU 或更小的模型。

**第四阶段（探索性）** 在字幕链路稳定后，再评估是否值得做音频替换，或者直接用后处理离线生成中文音轨。

## 几个容易踩的坑

- **Whisper 幻觉**：静音段会被“翻译”出无关文本。务必加 VAD，并对极短片段或低置信度结果做过滤。
- **音频重采样**：Whisper 期望 16kHz 单声道。`parec` 出来的可能是 48kHz 立体声，需要在送入模型前用 `librosa` 或 `scipy` 做重采样和混单，否则会影响识别质量。
- **PipeWire 与 PulseAudio 的工具混用**：Debian 12 上 `pactl` / `parec` 通常指向 PipeWire 兼容层，行为基本一致，但如果遇到 monitor source 名称异常，用 `pactl list sources short` 和 `pw-cli` 交叉确认。
- **逐句翻译的上下文丢失**：可以接受，但如果发现质量明显下降，考虑在翻译时带上前一句作为上下文。
- **不要过早追求“流式”**：Whisper 的“流式”本质是分块批处理，分块太短会牺牲准确率，太长会增加延迟。先用 2～3 秒的 VAD 段跑通，再根据体感调参。

**总结：你的“本地、系统音频输入、英译中、桌面显示”核心思路完全可行，技术栈也已经成熟（PipeWire monitor + faster-whisper + CTranslate2 翻译 + PyQt6 OSD）。音频替换中文语音在实时场景下延迟和音色保持问题难以绕开，建议作为远期后处理方案而非第一版目标。**
